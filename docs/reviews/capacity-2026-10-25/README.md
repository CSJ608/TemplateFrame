# 大文件与并发容量验证（2026-10-25）

## 结论

本轮是用户授权的合成容量验证，不是客户环境验收，也没有实现新的生产优化。生产代码与 `30e4ee4` 完全一致。

- **Excel 百万行导入：6 列主场景单任务通过，但进程峰值工作集约 4.5–5.0 GiB。** SimpleExcel 普通读取、正常定义名契约读取和模板 Excel 回读分别验证。
- **Excel 百万行导出：两条导出路径均未通过本轮 5 GiB 托管堆预算。** 50 万行通过；百万行在保存工作表 XML 时出现 OutOfMemoryException。不能解释成所有更大内存服务器都无法导出，但当前实现不具备已验证的低内存百万行导出能力。
- **Word 十万行导出：6 列纯文本、两个微小图片控件，通过。** .NET 8/10 单任务约 11.5–12.5 秒、峰值工作集约 1.8 GiB。未测试 Word 导入、Office/WPS 打开、排版或打印性能。
- **100 并发仅在每任务千行、6 列的批次验证通过。** 六条路径全部成功；每任务万行的 16 并发也成功。没有验证 100 个最大规模文件同时处理，不能把两种上限组合成承诺。
- 默认安全限额不能直接承担本轮上限，须按可信业务显式设置；生产默认值未放宽。

下一步应优先评估 Excel 流式导出，其次是按行/分批消费的导入接口，以及宿主的大任务并发预算。实施前需确认“100 并发”是同时接收任务、允许排队，还是要求 100 个最大文件同时执行。后者涉及独立的服务器/集群容量目标，不能从本机试验推导。

## 输入与方法

用户边界：Excel 导入/导出最多 1,000,000 数据行，Word 导出最多 100,000 数据行、最多两张图片，并发最多 100，Word 导入不测试。列数未指定，本轮明确取 6 列作为主场景，30 列只在万行单任务补充压力验证，**不是任意列宽的容量保证**。

Excel 每六列为四列唯一中文字符串、一列递增数值、一列日期；Word 为唯一中文字符串。Word 两个图片控件使用 1×1 PNG，只覆盖绑定路径，不代表大图资源成本。百万行导入文件约 30.2 MiB，工作表展开 XML 约 433.1 MiB，说明不能只用压缩文件大小估计内存。文件身份和展开大小见 [fixtures.json](fixtures.json)。

Word 接口提供两张业务图片，库填充后保留两份模板占位图片（各 570 字节）并新增两份业务图片，因此实测包有四个媒体部件、两个活动图片引用；不是声称包内只有两个部件。该额外约 1 KiB 占位资源不是本轮十万行内存问题的主要解释，未顺便修改图片替换语义。

环境：Windows 10、i5-12500H（16 逻辑处理器）、约 31.8 GiB 物理内存，开始时约 13 GiB 可用；SDK 10.0.402。主矩阵实际运行 .NET 10.0.13，另补 .NET 8.0.32 千行冒烟及部分大规模场景，均记录实际运行时。未测 net472 容量。见 [environment.json](environment.json)。

每个 case 独立进程、单次操作或单批并发，默认分层 JIT、Workstation GC、无预热。导出数据为每个任务独立物化，模板先生成；计时包含库处理和导出写盘/关闭，不含输入准备和校验。导入结果保留到全批结束再逐格校验。专用线程就绪后同一闸门放行；这是并发突发批次，不是 HTTP 服务、排队系统或持续吞吐压测。模板准备可能预热共享代码，文件系统缓存未清空，后台程序未关闭，不能拿这些时间与前轮稳态 BDN 数据直接比较，单次结果不构成 P95/P99/SLA。

进程工作集峰值优先采用成功子进程报告的 OS `PeakWorkingSet64`，包括输入准备、库调用和校验全部阶段；不是库独占内存，也不是累计托管分配。控制器另以约 100 ms 采样工作集/私有内存，每约一秒查询系统可用内存；查询可能延长间隔，采样值可能漏峰。早期 `smoke-*` 的采样很短且没有子进程 OS 峰值，只作为正确性冒烟，不用于容量结论。

本机保护：子进程 `DOTNET_GCHeapHardLimit=0x140000000`（5 GiB），采样私有内存上限 6 GiB，系统可用内存保留 4 GiB，每 case 最多 120 或 180 秒。后续日志直接记录 GC 报告的 5,368,709,120 字节预算。保护会影响 GC 行为，所以所有结果均为**此保护预算下**的观察，不声称无限内存时的极限。没有设置生产/系统环境变量。控制器低阈值自检 `guard-check` 成功终止指定子进程，不是业务性能失败。

## 单任务结果

下表使用 .NET 10、6 列。耗时为操作阶段，峰值为全进程生命周期；每格一次观察，不能用于精确版本性能比较。

|---|---:|---:|---:|---|
| SimpleExcel 普通导入 | 100,000 | 4.21 | 0.50 | 通过 |
| SimpleExcel 普通导入 | 1,000,000 | 32.75 | 4.52 | 通过 |
| SimpleExcel 定义名契约导入 | 100,000 | 4.16 | 0.53 | 通过，v2 输入 |
| SimpleExcel 定义名契约导入 | 1,000,000 | 35.71 | 4.78 | 通过，v2 输入 |
| 模板 Excel 导入 | 100,000 | 4.38 | 0.57 | 通过 |
| 模板 Excel 导入 | 1,000,000 | 44.38 | 5.04 | 通过，接近预算 |
| SimpleExcel 导出 | 100,000 | 4.23 | 0.68 | 通过 |
| SimpleExcel 导出 | 500,000 | 18.25 | 3.23 | 通过 |
| SimpleExcel 导出 | 1,000,000 | — | — | 堆预算内内存不足 |
| 模板 Excel 导出 | 100,000 | 5.45 | 0.87 | 通过 |
| 模板 Excel 导出 | 500,000 | 23.69 | 3.98 | 通过 |
| 模板 Excel 导出 | 1,000,000 | — | — | 堆预算内内存不足 |

百万行导出的进程总耗时分别约 38.6 / 64.3 秒，然后报告内存不足；采样私有内存约 4.87 / 5.04 GiB。堆上限不同于进程私有内存上限，非托管内存也计入进程，不能据此声称“内存限制失效”。异常栈均到达 OpenXML DOM 保存及 MemoryStream 扩容，说明完整 DOM 加 XML 保存缓冲是后续应验证的重点；没有使用堆转储精确分解每类对象占比。

.NET 8 补测：百万行 SimpleExcel 普通导入约 35.63 秒、4.52 GiB；十万行 Word 导出约 12.50 秒、1.78 GiB；十万行 SimpleExcel/模板 Excel 导出分别约 4.48 / 5.86 秒。两运行时顺序与样本不同，不宣称运行时优劣，也未把全部 .NET 10 结果推广至 .NET 8。

30 列、万行单任务六条路径均通过：Excel 操作约 2.09–4.17 秒，峰值约 0.26–0.42 GiB；Word 约 6.18 秒、0.92 GiB（PNG 修正后）。未运行 30 列的百万行 Excel 或十万行 Word。

每任务千行的 4 / 16 并发先行验证，也全部通过。各任务有独立输入数据/服务/流，导出单独文件；导入结果逐格验证，导出检查 ZIP/XML 结构、精确行/单元格数、末行标记和 Word 两个图片引用，**不是对全部导出单元格值及 Office 视觉布局的完整验收**。

## 样本修正与不利结果保留

初始生成器 `6451645` 把 SimpleExcel 的 `Items_Cn` 定义名写成数据范围；正常契约布局要求它指向单个表头，因此走了按表头回退。初始 `smoke-contract-read`、`smoke8-contract-read`、`net10-contract-read-10000-c1`、`net10-contract-read-100000-c1`、`net10-contract-read-1000000-c1` 均应按**回退路径**理解，不能作为正常定义名性能。

修正提交 `451d608`：`Items_Cn` 指向表头，模板 Excel 的 `TF_Items_Cn` 继续指向数据范围，工作表内容不变。后续 `v2-contract-*`、全部并发和宽表契约测试使用修正输入。初始其他读取路径不受该定义名差异影响。所有旧结果保留，没有覆盖或只挑有利数据。

回退路径百万行在 5 GiB 堆预算内内存不足，十万行峰值约 0.94 GiB；修正后正常定义名路径十万行约 0.53 GiB、百万行通过。源码显示布局判断可在加载工作表后才决定回退，随后重新打开读取；这是后续可单独验证的重复加载候选，不把该差异归因为本轮生产代码优化，也不把它推广到所有无定义名文件。

收尾进一步检查发现最初 1×1 PNG 的 IDAT CRC 不正确，早期 Word 只验证了绑定和结构，没有验证图片内容。`61b1b0f` 替换为校验通过的图片，增加扫描行与导出引用字节验证，并重跑关键 Word 矩阵。最终 Word 数字全部来自 `pngv2-*`；[excluded-cases.csv](excluded-cases.csv) 列出的 11 个旧 Word case 保留原始输出，但汇总标为 `invalid-image-fixture`，不作为有效容量证据。也重测了默认 Word 限额拒绝。没有把输入错误解释为库缺陷。

## 交付、复现与后续决策

93 个进程 case：64 个有效输入的操作批次校验通过、5 个默认限额预期拒绝、3 个堆预算内内存不足、1 个控制器低阈值终止自检、9 个输入生成、11 个旧图片样本 case 排除。不是 93 次同场景重复采样。完整 [summary.csv](summary.csv)、[原始记录](raw) 包含失败，生成的办公文件留在忽略目录 `artifacts/capacity-2026-10-25`，未提交大文件；失败及排除样本的输出不应使用。

探针与命令见 [使用说明](../../../test/TemplateFrame.CapacityProbe/README.md)。先构建，按 case 记录的 Mode/Rows/Columns/Concurrency/Framework/Limits 复现；必须使用新目录，不要在一次矩阵中并行运行多个 case。当前生成器默认产生 v2 输入；回退路径要用初始提交的生成器或把相应列定义名改为数据范围重建，不能用 v2 输入冒充初始结果。ZIP 元数据/生成标识可能不同，fixtures.json 的哈希标识本次实测文件，不承诺每次生成字节一致。

后续建议顺序：

1. 明确并发语义与部署预算：允许同时接收 100 个任务并排队，与 100 个最大文件同时执行是不同目标。
2. Excel 导出优先评估流式工作表写入，保留现有模板/样式语义；若再提供按行输入接口，应独立讨论 API，而不是悄悄修改既有契约。
3. 大导入若要降低常驻内存，应评估逐行消费/分批接口；当前返回整张结果的数据契约本身就需要保留大量对象。
4. Word 先保留当前实现，通过显式限额、宿主排队和输出文件可用性验收控制风险；本轮没有证据要求重写 Word 引擎。
